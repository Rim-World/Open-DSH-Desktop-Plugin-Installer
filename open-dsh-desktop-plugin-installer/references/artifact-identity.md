# 产物身份核对：你拿到的东西 ≠ 你要装的那个包

阶段 2 回答"该不该装"（声明的支持范围、类型、客户端版本）。这一节回答更前面的一件事：**你手上这个来源，装出来到底是哪个包**。两者都是写盘前的门，都可能在汇报之后被用户叫停。

插件通常以"一个仓库地址 / 一个 tarball / 一句包名"的形式被交到你手上，而这三者都不保证等于包本身：仓库可以改名、包可以改名、同名包可以属于另一个项目、默认分支可以和发布产物不是一回事。**先把身份钉死，再谈兼容性。**

## 1. 读产物自己的清单，不要读它的名字

不管来源是 URL、本地目录还是 tarball，先把它解开或定位到，读它自己的 `package.json`：

| 字段 | 为什么先看它 |
|---|---|
| `name` | **依赖表和 `dsh.profile.bundles` 都用这个名字**，不是你输入的那个字符串 |
| `version` | 报告里写的版本以它为准；`-preview` / `-beta.N` 这类后缀要如实转述，别当成正式版吞掉 |
| `private` | `true` 表示它不通过 registry 分发——"从 registry 装同名包"这条路必然装到别的东西 |
| `dsh.bundle.patch` | loader 契约。没有它就不是 bundle 插件，装了也不激活任何层 |
| `exports` / `main` | 宿主半边与浏览器半边的入口产物路径 |

**名字对不上就停下**：如果你被给的标识（仓库名、文件名、口述的名字）和清单里的 `name` 不一致，把两边都讲清楚、让用户选，不要自己认定"应该就是它"。装错包和装不上一样贵——它会把一个来源不明的依赖写进 profile，而报告里那一行会和你声称装的东西对不上。

## 2. 尊重作者声明的分发通道

作者写明的通道是事实描述，不是建议。三种常见情形各有一条硬边界：

- **只发 Release 附件**（清单里通常 `private: true`）：registry 上同名或近名的包**不是这个项目**。别用"名字看起来对"替代核对。
- **只发 registry**：那就用包名 + 版本；改用 git 源反而会拿到未发布的开发状态。
- **仓库根直接 clone**：作者一般会写明"需要自己构建"。先确认构建产物是否随仓库提供；没有产物时 `github:` 装法可能装出一个加载不起来的包。

作者同时声明了"唯一来源"时，就按那一条走，并在报告里写清楚你走的是哪条。

**别用名字筛产物**：仓库名可以只是仓库名（与包名不同是常态），而作者在**某次大版本里换掉附件名前缀**也是允许的——同一个项目相邻的两个大版本，附件可以叫完全不同的名字。判断"这个附件是不是我要的"，看的是**解出来的清单 `name` / `version`**，不是文件名像不像。

## 3. 默认分支 ≠ 发布产物

发布之后默认分支通常还会继续提交，所以二者可能指向不同的代码：

- 用 GitHub API 或 `git ls-remote` 把 **tag 解析成 commit sha**，再和默认分支的 HEAD 比一比；不同的时候，"跟随 HEAD"装到的是发布**之后**的代码。把这件事讲给用户，而不是替他挑一个。
- 反过来，只跟 tag 也可能比作者当前推荐的更旧。这层不确定性属于用户的选择，不属于你的判断。
- **能钉提交就钉提交**（`github:<owner>/<repo>#<sha>`，或发布产物的固定 URL）。留在 profile 里的是一个长期引用，浮动分支意味着以后每一次安装都可能带进一个从未核对过的提交。

## 4. 有校验和就核校验和

作者发布校验和时，**下载完先算一遍再装**，并把结论写进报告。这一步很便宜，而且是唯一能区分"我装的就是作者发布的那个文件"和"我装了一个看起来同名的东西"的证据。

```powershell
(Get-FileHash <file> -Algorithm SHA256).Hash.ToLower()
```

清单本身也要当数据看：从 HTTP 取回的校验和文件可能是字节数组而不是文本，先转成字符串再逐字比对，否则会得到"不匹配"的假结论。

## 5. bundle 插件的三个名字必须自洽

这是唯一能在**离线**状态下预判"装上会不会在客户端启动时崩"的检查，值得单独做一遍：

| # | 名字 | 在哪里 |
|---|---|---|
| 1 | 包名 | 清单的 `name` |
| 2 | 装配条目名 | 它 `dsh.bundle.patch` 指向的补丁文件里那条 entry 的 `name` |
| 3 | 客户端注册 id | 浏览器半边（`exports["./client"]` 指向的文件）向客户端模块系统注册自己时用的 id |
| 4 | 浏览器半边的导出名 | 同一个入口里 `export const name = …` 之类，被客户端模块系统用来对号的名字 |
| 5 | 生产者标识 | 宿主半边里那些自报家门的常量（例如 `PRODUCER_KIND`、路由前缀、`PACKAGE_NAME`） |

一个项目**改名**时这几处必须一起改。漏掉第 3–5 处尤其隐蔽，因为两套系统在不同时刻检查它：

- 宿主的 Loader 只按第 1、2 处装配，所以**宿主半边照样挂得上、状态照样 `live`、诊断照样为空**；
- 客户端模块系统要到**客户端启动**时才发现注册键对不上。它按**包名**生成 loader row id，却按插件**自己注册的 id** 去找——两者不同名时，那条 entry 整条判为"没有激活"（表现为该插件的面板/卡片/设置页全都不出现），启动报重复注册或 entry id 不匹配。

**已有一个真实案例就是这条**：某插件在 0.8.0 里把 `package.json` 的 `name` 改了，但浏览器半边的注册 id 与导出名还是旧名，于是宿主半边一路 `live`、诊断为空，而客户端半侧从不激活；作者在 0.8.1 里补正了这两处。所以当用户说"装了、也 live，但界面上什么都没有"时，先数这几处名字，而不是去翻依赖树。

注意症状有两种强度：名字对不上**可能**让客户端整体起不来，也**可能**只是让这一个插件不出现（客户端照常启动、不报错）。**别把"客户端起来了"当成"这个插件挂上了"**——想知道客户端侧到底发生了什么，读它自己的启动日志（见 `verification.md` 第 6 节），而不是从"没崩"推"没问题"。

于是现象是"装完当次一切正常，一重启客户端起不来"。本地目录和 tarball 都能查第 3–5 处，直接读那几个文件即可：

```powershell
Select-String -Path "<pkg>\lib\client.js" -Pattern "__ModuleLoader__|load\(" |
  Select-Object -First 5
```

**接入方式也只能选一种**：把包名写进 `dsh.profile.bundles`，**或者**在用户的 `cordis.patch.yml` 里手写一条 `insert`。两者都做会让同一条 entry 插两次（启动报重复 entry id）。动手前先看用户那一层里有没有已经存在的同名 entry。

## 6. 本地产物要留得住

从本地文件安装（`file:` 依赖）时，依赖表里记的是**路径**：

- 把产物放到 profile 里一个稳定位置（例如 `<profile>\.dsh-tarballs\`），不要留在"下载目录"这类随时会被清掉的地方；
- 在最终报告里写明**这个文件必须留着**——删掉它，之后任何一次 `pnpm install` 都会以找不到文件失败；
- 从 registry 或 git 源安装不涉及这条。

**换成新版之前，先用校验和证明"手上这份是谁"**：把当前落盘的那份产物算一次 sha256，和它所属版本发布时作者的校验和比一比。一致 → 你换的是官方产物，这是一次可控替换；不一致 → 先停下问清楚来源（可能是自己打的包、被改过、或根本不是这个项目），此时"更新到最新"可能是在覆盖一个你并不知道来源的东西。版本号相同不代表内容相同（本地重打包、同版本不同构建都能改内容），校验和能区分。

## 7. 报告里要出现的一行

```text
产物：<name>@<version>（来源：发布附件 / registry / 本地 tarball / git 提交 <sha>）
校验：<与作者发布的 sha256 是否一致，或"作者未提供">
身份：<你被给的标识> 与清单 name <一致 / 不一致（已交用户确认）>
自洽：包名 / entry name / 客户端注册 id <三处一致 / 不一致（见 verification.md 的冷启动一节）>
```
