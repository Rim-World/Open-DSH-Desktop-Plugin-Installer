# 更新发现与本地产物替换

前几节讲的是"怎么装"。这一节讲两件更容易做错的事：

1. **怎么知道"有更新"**——"已是最新"这个结论，往往不是观测到的，而是**一个接口沉默**换来的；
2. **怎么把本地产物换成新版**——`file:` 依赖更新的是**文件与路径**，不是版本号，没有 `pnpm add` 那条捷径。

用户问"有几个插件能更新 / 帮我更新一下"时，先读这一节。

## 1. 更新有三个互不相通的通道

不存在"一个接口告诉你全部插件是否最新"。每个包只在**它自己的分发通道**上有版本可比：

| 通道 | 判断依据 | 典型写法 |
|---|---|---|
| registry（npm） | 包名 → semver | `"name": "1.2.3"` |
| git 仓库 | 提交 sha（tag 或默认分支 HEAD） | `github:owner/repo#<sha>` |
| **发布附件**（Release asset） | **附件文件名里的版本号 + 作者给的校验和** | `file:.dsh-tarballs/<asset>.tgz` 或发布产物的固定 URL |

前两条有现成的接口可查；**第三条没有任何接口认它**。

### 市场表格对本地产物是沉默的，不是否定的

市场把每个包分成 `npm` / `github` / `linked` 几类，并给出 `current` / `latest` / `updateAvailable`。**本地 tarball 属于 `linked`：它的 `current` 与 `latest` 都是空的，`updateAvailable` 恒为 `false`。**

于是会出现这样的组合，而且它是**正常的**：

```text
<包名>   kind=linked   current=(空)   latest=(空)   update=False
```

**`false` 在这里的意思是"我不知道"，不是"它是最新的"。** 把这一行读成"无需更新"，就是本节存在的理由。报告里凡是有 `linked` 类的包，都要单独说明："它的版本信息不在这个接口里，我按发布通道核对过/未核对。"

顺带记住这个接口自己的两个分母，它们能把"没什么可更新"和"什么都没看"分开：

- `updates/summary` 的 `checked`（**扫了几个包**）与 `updatable`（其中几个有更新）——`updatable: 0` 只有在 `checked` 等于你预期的包数时才说明"都看过了、没有更新"；
- 逐包表格用 `GET /dsh-market/updates?force=1`（`kind` / `current` / `latest` / `updateAvailable` 都在里面），`force=1` 顺带刷新缓存。**报告里引用 `checked` 比只引用 `updatable` 诚实**。

**这类行可能仍有一个 `version` 字段**（本地产物的落盘版本回显），而 `current` / `latest` 是 `null`。`version` 可以当"本地现在是哪个版本"的快捷提示，**但它不是上游答案**：该包是 `0.8.1` 而上游已发 `0.9.0` 时，这个字段照样写 `0.8.1`、`updateAvailable` 照样是 `false`。别把"字段有值"误当成"接口给过结论"。

### 上游地址缺失时怎么找

本地产物常常**没有 `repository` / `homepage`**，`private: true` 又意味着 registry 上根本没有它——"回到它自己的分发通道"这句会在这里落空。地点可以从产物自己身上挖出来，按成本从低到高：

1. **profile 的依赖行**：`file:` 后面只是个文件名，通常就在文件名里带着包名与版本；**文件名也是版本比对的第三个来源**（新版会带新版本号）。
2. **产物内的文档**：`README` / `HELP-*` / `CHANGELOG` 里常直接印着 Releases 链接或安装指引，`grep` 一次就有。
3. **日志里的历史 URL**：`<profile>\.plugin-manager\logs\*\pnpm.log` 与 `.dsh-market\log.ndjson` 里往往留着这个包**以前用 git 源或 URL 装过**的痕迹（`codeload.github.com/<owner>/<repo>/...`），仓库名与 sha 都在里面。
4. 还找不到就**停下问用户**——不要猜一个仓库去比对版本，那等于用一个未知来源的版本号给用户下结论。

拿到仓库后，**用 GitHub 的 `asset.digest` 做一次零下载核验**：Releases API 对每个附件给出 `digest: sha256:…`，与你本地算出的 sha256 直接比即可，不必为了核对而下载几十 MB 的附件（只有当真要换新版时才需要下载）。

### 三类通道分别怎么核对

- **npm**：`latest` 与落盘版本比对；镜像可能滞后，必要时问官方 registry 而不是镜像。
- **git**：解析默认分支 HEAD，与 profile 里钉住的 sha 比对（`plugin-compat.mjs` 与宿主接口都能给出当前 sha）。注意**默认分支 HEAD 不等于发布产物**——仓库 HEAD 往前跑而作者只发附件时，两条通道的"最新"不是一回事。
- **发布附件**：读仓库的 Releases（`GET /repos/<owner>/<repo>/releases?per_page=N`），**先看 `draft` 与 `prerelease`**：草稿不是发布；标了 prerelease 的版本要不要上，属于用户的选择，不是你的判断。取"版本号更高、正式发布、附件名与本地那份同族"的那一个，再核校验和。

判据要落到**版本号/提交号本身**，而不是"附件存在"。顺带留个心眼：作者可能在某次大版本里**换掉附件名的前缀**——同一项目的附件在相邻大版本之间可以叫完全不同的名字。别按名字过滤，按清单里的 `name` 过滤。

### 结论怎么写

发现更新后，先分清两件事再写报告：

- **可检测**：旧版本是 X、上游是 Y（附证据：提交号 / 版本号 / 附件名 + 校验和）；
- **可安装**：X → Y 属于哪条通道，是否需要换 `specifier`（npm 换版本号、git 换 sha、本地产物换文件名），是否有构建步骤。

然后**停下，让用户决定装不装**。更新是替换一个正在被第三方代码引用的包，它不是无风险的操作；用户让你"更新能更新的"，指的是动手，不是替他承担版本选择。

## 2. 装之前先证明你手上这份的来源

更新场景有个特有的便宜证据：**把当前落盘的那份文件算一次 sha256，与它所属版本发布时作者的校验和比一比。**

- 一致 → 你手里这份确实是官方产物，后面换新版才是"可控替换"；
- 不一致 → 先停下。说明这份产物不是来自那个发布（可能是自己打的包、被改过、或根本是别的项目），此时"更新到最新"可能是在覆盖一个你并不知道来源的东西。

这比读版本号强：版本号可以相同而内容不同（本地重打包、同版本不同构建），校验和不能。

做这件事有两种成本，按你手上已有什么选：

- **作者给了校验和附件**（例如 `SHA256SUMS-<version>.txt`）：把它读进内存即可，不必下载产物本身。清单很小，直接取来比较。
- **只有 GitHub API**：Releases 的附件对象会带 `digest: sha256:…`，**零下载**就能核。
- 若 `pnpm-lock.yaml` 里那条 `file:` 依赖带 `integrity`（sha512-base64），把它解出来和同一个文件比一次——一致就说明 `node_modules` 里那份确实是**从这一个文件**解出来的（否则可能存在"文件换了但依赖树还是旧的"）。

**运行中该不该动**：比校验和只是读数，随时可做；但在你还没打算换版本时**不要顺手下载附件**——没有要换的东西就没有下载的理由。

## 3. 本地产物（`file:`）怎么换版本

本地产物的依赖表里记的是**路径**，所以"更新"= 换文件 + 改那一行路径。步骤：

1. **下载到工作区**，先验证，再进 profile：

   ```powershell
   Invoke-WebRequest <asset-url> -OutFile <workspace>\<asset>.tgz -TimeoutSec 900
   (Get-FileHash <workspace>\<asset>.tgz -Algorithm SHA256).Hash.ToLower()   # 与作者校验和比对
   ```

   大附件用重试循环包一层（见第 5 节），并对返回值验长度——别只看命令有没有报错。

2. **把新文件复制进 profile 的稳定位置**（例如 `<profile>\.dsh-tarballs\`），再对 profile 内的副本验一次哈希。校验和应该对着"最终留在盘上的那一份"算，不是对着下载缓存算。

3. **旧文件先留着**，不要删。回滚要用它，而且 `node_modules` 里那份是从它解出来的。

4. **结构化改依赖行**（路径改了，文件名通常也改）：

   ```json
   "pkg-name": "file:.dsh-tarballs\\<new-asset>.tgz"
   ```

   照例：改完**立刻**解析校验（`ConvertFrom-Json` / `JSON.parse`），再读一次宿主接口确认它读到的 specifier 已经变了。

5. **用离线安装落地**：

   ```powershell
   node <pnpm.mjs> install --offline
   ```

   `file:` 依赖的更新**不需要网络**——本地文件就在盘上。用 `--offline` 的好处是：它不会顺手去重新解析依赖树里那些远端依赖（git 源、registry 包）。**这一步很值得做**：正常 `install` 会顺带 HEAD/GET 所有为 `github:` / URL 的依赖，一个远端超时就能让整次操作失败，而你要的只是替换一个本地文件。真缺包时 pnpm 会明确报错，再摘掉 `--offline` 重跑即可。

6. **验证**（照 `verification.md` 的清单，另加两条）：

   - `node_modules/<pkg>/package.json` 的 `version` 是新版本；
   - lockfile 里**旧文件名 0 处引用、新文件名有条目**（`Select-String` 两个方向都数一遍）。

7. **报告**：换了哪条依赖行、新旧版本、校验和是否一致、旧文件还在哪（回滚用）、是否需要重启。

## 4. 更新完，"要不要启用"是另一个问题

更新只动**依赖与文件**。一个包可以**装了但没启用**（不在 `dsh.profile.bundles` 里），此时：

- 更新它是有意义的（下次启用就是新版），但**更新不会顺带把它启用**；
- 宿主对它的状态串会写"已停用(市场开关或补丁层)"这类**聚合原因**，它是"没在 bundles 里"的笼统说法，**不等于用户主动关过它**——市场自己的禁用清单可能是空的。

所以：

- **不要**从状态串推断用户意图，也不要顺手把它加进 `bundles`；
- 更新完成后把"它现在是启用还是停用"如实告诉用户，并问一句要不要启用（启用会改变每个会话的行为，是用户的决定）；
- 反向也成立：**用户说"更新"时默认只更新，不要连带启用**。两件事分开说、分开做。

## 5. 取件的三条环境经验

- **发布附件与源码 tarball 不是同一个下载主机**：`codeload.github.com`（`github:` 与 `/tar.gz/<sha>` 走它）直连常挂到超时，而 Release 附件走另一条路径，往往通畅。同一个仓库，一条通道超时、另一条能下载，是完全可能的——**不要因为一条通道失败就判定"这个仓库拉不动"**。
- **重试要包住"整次下载"，并且每次重试都给足超时**。21 MB 量级的附件在国内链路上耗到一分钟以上很常见，`--fetch-timeout` 那套参数只对 pnpm 生效，手工 `Invoke-WebRequest` 要自己给 `-TimeoutSec`。
- **失败过的操作会留下记录，去读它**：`<profile>\.plugin-manager\logs\<op>\pnpm.log` 与 `<profile>\.dsh-market\log.ndjson`。同一条命令之前失败过时，那里通常已经有**真正的报错文本**（例如某条 URL 超时），而用户转述给你的原因可能只是猜测。**开工前先搜一遍这两个文件**，成本极低，能省掉一次盲目重试。

  检索时**别只搜包名**：仓库名、附件文件名、提交 sha 都可能出现，而它们常常与包名不同（本地产物尤其如此——它的包名与仓库名可以毫无关系）。按包名搜到 0 命中**不能**推出"没有失败记录"，换仓库名/文件名再搜一次；反过来，命中一条 URL 也就顺带把上游地址找到了（见上一节）。

## 6. 写命令时的两个自伤陷阱

这两条都真实发生过，特征是"命令报的错与它实际做的事无关"：

- **PowerShell 双引号里 `$var:` 会被当成作用域限定符**。`"branch $b: no"` 会解析失败（报"变量引用无效"），而不是输出字符串。把变量写成 `${b}`：`"branch ${b}: no"`。这类错误会让整条命令退出，看起来像"操作失败"，其实只是字符串写法。
- **控制台编码可能与文件编码不同**，中文输出显示成乱码。**乱码是显示层的问题，不代表文件坏了**：校验文件好坏要看解析结果（`ConvertFrom-Json`）或哈希，不要因为终端里看到乱码就动手重写文件。需要干净输出时显式设一次 `[Console]::OutputEncoding`，或者把结果写进文件再读。

## 7. 报告模板

```text
更新发现：核对通道 <registry / git / 发布附件>；市场接口对本地产物无版本信息（kind=linked）
可检测：<旧版本或提交> -> <新版本或提交>（发布状态：正式 / 预发布 / 草稿）
来源证明：当前落盘产物 sha256 <与作者校验和一致 / 作者未提供 / 不一致——已停下>
可安装：通道 <...>；需要改 <依赖行 / specifier / allowBuilds 键>；构建 <需要 / 不需要>
启用状态：装好了但 <启用 / 仍停用——是否启用请用户决定>
回滚：旧产物仍在 <路径>；回滚 = 还原 <文件清单>
重启：<需要 / 不需要>（带浏览器半边的插件替换文件后必须冷启动才算验证）
```
